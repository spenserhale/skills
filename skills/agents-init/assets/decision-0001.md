## Context

Decisions, specs, and plans that live in chat history or in someone's head get lost, and coding agents drift from intent they cannot read. Humans and agents need one place to learn what the product does, why it works that way, and how each change was planned, and that place has to change in step with the code.

## Options considered

1. **Markdown in the repo**: versioned with the code, readable by every agent, reviewed in the same pull request as the change.
2. **An external wiki or tracker** (Notion, Confluence, issue threads): richer editing for non-engineers, but it drifts from the code and agents cannot see it without extra tooling.
3. **A docs framework from day one**: a rendered site immediately, at the cost of tooling before there is content.

## Decision

We keep durable docs in the repo as Markdown with Starlight-compatible frontmatter: living feature specs in `<specs path>`, decision records in `<decisions path>`, change plans in `<plans path>`<, product docs in `<product path>`, if created>, and engineering guides in `<guides path>` as each domain gets real policy. <One of: "A Starlight site in `site/` renders the same files." / "A Starlight site can render these files later without rewriting them." / "Customer-facing docs stay in `<existing docs site>`; these docs are for building the product."> <If an earlier record adopted decision records: "This builds on <NNNN>, which adopted decision records; it does not supersede it.">

Every commit is atomic: the code, its tests, and the docs it changes land together. Strong decisions get a record in `<decisions path>`; records are superseded, never rewritten.

<One of: "The setup took the recommended defaults at the owner's request." / "The setup ran headless for <name>, so it took the recommended defaults." / "The owner chose:">

- **Structure**: <default, or customized (name the changed paths)>
- **Viewable site**: <Markdown only, a Starlight site in `site/`, or not asked because `<existing docs site>` exists>
- **Product docs**: <vision only, vision and pricing, or none, and why>
- **Changelog**: <`CHANGELOG.md` by hand, generated by the existing tool (name it), or none>

## Consequences

- Agents read the relevant spec and decisions before changing behavior, and reviewers see doc changes next to code changes.
- Updating a spec or writing a decision record is part of each change, which costs a few minutes per change.
- Specs describe current behavior only; planned behavior lives in plans until it ships.

## Revisit when

People who do not work in the repo need to edit docs directly, or the structure stops matching how work is planned.
